# cc-dynamic LP project structure — per-product vs boilerplate

What the scaffold customizes vs what it copies verbatim from the reference template.

## Top-level

| Path | Role | Per-product? |
| --- | --- | --- |
| `.env` | page/country/strategy/service | **Yes** (page, country, service, scenariosConfig) |
| `config.json` | strategy/flow/slug/service fallback | **Yes** (`flowConfig.slug`, `flowConfig.service`) |
| `package.json` | scripts (ouisys-clients) + deps | No (verbatim) |
| `ssr-dynamic.js` | Node SSR renderer | No (verbatim) |
| `tsconfig.json`, `.babelrc`, `.browserslistrc`, `.nvmrc`, eslint/prettier | build/lint config | No |
| `README.md`, `docs/`, `*.png` screenshots, `.firecrawl/`, `.playwright*` | docs/scratch | Dropped by scaffold |

## src/

| Path | Role | Per-product? |
| --- | --- | --- |
| `index.html` | HtmlWebpackPlugin template (`#root`, GTM, error beacon) | Mostly no; title/og via `.env` |
| `index.tsx` | client entry — `createRoot(#root).render(<Root/>)` | No |
| `index.ssr.ts` | SSR entry — re-exports `Root` (symlinked across pages) | No |
| `Root.tsx` | page composition; SSR loader; comp/non-comp gate; **checkout slot** | **Wiring point** |
| `providers/RootContext.tsx` | reads `pageConfigs`; synchronous comp/non-comp; slug/locale | No (uses runtime config) |
| `providers/ProvidersWrapper.tsx` | redux + Suspense + Root + i18n | No |
| `__doNotModify/*` | generated store/flows/reducers/components | No (never edit) |
| `components/*` | Hero, ContentGrid, Features, HowToSubscribe/Unsubscribe, HeroPricing, Footer, Menu, Loader, etc. | **Presentation is per-product** (copy/imagery); plumbing components are boilerplate |
| `styles/_variables.scss`, `styles/Root.scss` | theming tokens + fonts | **Yes** (colors, fonts) |
| `assets/logos/<serviceId>.{svg,png}` | service logo (resolved by `serviceId`) | **Yes** |
| `assets/imgs/<serviceId>/*` | product imagery | **Yes** |
| `localization/extractedMessages/en.json` | English source copy | **Yes** (copy) |
| `localization/translations/*.json` | compiled locales | Generated via `manage:translations` |

**Module-scope reads of `pageConfigs`/`window.configJson`-derived values are a trap, and production
hides it.** The backend injects `window.configJson` into the HTML before the bundle runs, so a
module-scope read works in prod and fails everywhere else (local dev, SSR, late injection). If this
page bills more than one `service.id`/MID through one build, this has bitten twice already:
- `Hero`/`Footer` resolving the logo with a bare ``require(`../../assets/logos/${serviceId}.svg`)``
  at module scope throws on import for any id you haven't shipped an asset for and blanks the WHOLE
  page before React mounts. Use a three-level fallback chain:
  `require(svg) → catch → require(png) → catch → require(FALLBACK_SERVICE.svg)`, and read
  `service.id` as `pageConfigs?.service?.id` (optional all the way down).
- A Google Pay `paymentRequest` built at module scope instead of inside a per-render
  `buildPaymentRequest()` call froze at all-`undefined`, throwing `DEVELOPER_ERROR in isReadyToPay:
  allowedCardNetworks must be setup` and permanently hiding the button.
Add a `console.error` naming the missing id/value so a silent fallback doesn't mask a real panel
misconfiguration. Rule: **always read config at call time, never at module scope.**

## The checkout slot (wiring point)

The reference template renders the native engine flow — roughly:

```tsx
// Root.tsx (reference)
const renderStrategy = () => strategy({
  identifyInitialState: () => <Loader />,
  creditCardFlow: () => <FLOWS.CreditCardFlow />
})(currentState);
```

For a cc-payment-integration page, mount the generated checkout in the comp branch instead of (or in
place of) `<FLOWS.CreditCardFlow/>`:

```tsx
import CheckoutSection from './CheckoutSection'; // generated by the scaffold
// …inside the comp branch where the payment card belongs:
<CheckoutSection />
```

`CheckoutSection` renders cc-payment-integration's `PaymentPage`, which already implements the
synchronous comp/non-comp decision, loader gate, prices-from-pageConfigs, card + wallets, and the
direct API posts — so the engine flow is no longer needed. Keep the template's outer SSR loader and
`html.is-noncomp` handling; they are complementary.

The scaffold marks the intended spot with `{/* CC_PAYMENT_MOUNT */}` and writes `PAYMENT_WIRING.md`
with the precise edit for the chosen base template.

## Theming tokens (`styles/_variables.scss`)

Reference tokens: `$spacer, $highlight, $primary-hover, $text-dark, $text-muted, $text-secondary,
$bg-light, $bg-surface, $border-color, $card-color, $border-radius`, plus breakpoints. The scaffold
overrides `$highlight` (primary), `$primary-hover`, and surface/border colors from the branding
inputs, and swaps the Google Fonts import in `Root.scss` for the chosen font.
